# Data formats

All game data lives in [`../data/coe`](../data/coe) as Xilinx `.coe` files. This page documents
the file syntax and the meaning of every word, so the data can be inspected or regenerated.

## COE syntax

A `.coe` file is plain text:

```
;30k*12
memory_initialization_radix=16;
memory_initialization_vector=
58C 58C 59C 59C ... ;
```

- Lines starting with `;` are comments (the first line is just a size note).
- `memory_initialization_radix=16;` selects hexadecimal.
- Every value is written MSB first, without `0x`, separated by whitespace.
- The vector is closed by a final `;`.
- Values are right-aligned to the memory width: 3 hex digits = 12 bits, 6 = 24, 8 = 32,
  16 = 64.

The initialisation file may be shorter than the memory: uninitialised words read as zero.

## File inventory

| File | Words | Capacity | Word layout | Used by |
| --- | --- | --- | --- | --- |
| `r1.coe` | 102,400 | 262,144 | `RGB444` | `mammap` background ROM |
| `beginphoto.coe` | 30,000 | 32,768 | `RGB444` | `memvmap` framebuffer |
| `putd.coe` | 1,024 | 1,024 | `RGB444` font pixels | `memscore` font ROM |
| `sin.coe` | 360 | 512 | `{cos[15:0], sin[15:0]}` | `memsin` direction table |
| `music3.coe` | 182 | 512 | `{time[19:0], note[3:0]}` | `memmusic` song table |
| `road6.coe` | 1,000 | 1,024 | 64-bit track records | `memroad` track table |

The capacities are the address widths used by the RTL (`memscore` 10 bits, `memroad` 10 bits,
`memsin`/`memmusic` 9 bits, `memvmap` 15 bits, `mammap` 18 bits).

## Backgrounds: `r1.coe`

The first 90,000 words are three 200×150 RGB444 pages (page 0 = `r1.png`, page 1 = `r2.png`,
page 2 = `r3.png`); the remaining 12,400 words are zero. `Solve` adds `BLOn` to the pixel
address in 30,000-word steps to switch pages.

Each word is `{R[3:0], G[3:0], B[3:0]}`; the VGA output uses the same bit order
(`rgb[11:8]` = red, `rgb[7:4]` = green, `rgb[3:0]` = blue).

## Title screen: `beginphoto.coe`

A single 200×150 RGB444 image. The framebuffer is initialised with it, so the title is visible
before the renderer writes its first frame.

## Font: `putd.coe`

The font was generated by `tools/legacy/tranp.cpp`. It contains the digits 0–9 as 5×7 glyphs
padded into a 9×10 cell (10 rows of 9 pixels), stored one pixel per 12-bit word. `Getdot`
addresses it as `y*9 - 9 + digit*90 + x`, which is why the stride is 9.

## Direction table: `sin.coe`

360 words, one per degree:

- `[31:16]` = `cos(θ)` as a signed 16-bit fixed-point value
- `[15:0]` = `sin(θ)` as a signed 16-bit fixed-point value

`Getsin` registers the word and exposes the two halves as the local track direction.

## Song table: `music3.coe`

182 notes, each 24 bits:

- `[23:4]` = note start time, in units of `WIDTH` clocks where `WIDTH` is the current
  clocks-per-percent value (`cpp`) from `speeder`
- `[3:0]` = note number: 0 = rest, 1..7 = do..si, bit 3 = high octave

`Music` compares the time field against its song timer and pushes the note to the audio
generator. The time unit is tied to the game speed on purpose: selecting a faster speed also
plays the song faster.

## Track table: `road6.coe`

1,000 64-bit words:

| Range | Meaning |
| --- | --- |
| 0–19 | segment headers: low 16 bits = number of notes in the segment |
| 20–999 | note records |

A note record is:

| Bits | Field |
| --- | --- |
| `[63:48]` | `x` position (0..199) |
| `[47:32]` | `y` position (0..149) |
| `[31]` | track direction (0 = forward, 1 = reversed) |
| `[30:16]` | duration / time to the next note |
| `[15:0]` | angle offset used when drawing the note |

The shipped table has two non-empty segments (49 and 95 notes); the other headers are zero.

## Regenerating images

[`../tools/image2coe.py`](../tools/image2coe.py) converts one or more images into an RGB444
`.coe` file:

```bash
python tools/image2coe.py data/images/r1.png data/images/r2.png data/images/r3.png \
    -o data/coe/r1.coe --width 200 --height 150 --pad 102400
```

It quantises each channel to 4 bits, writes 3 hex digits per pixel and pads with zeros to the
requested word count. The result is functionally equivalent to the original images, but it is
not guaranteed to be byte-identical to the shipped file.

## Legacy generators

The original data pipeline used three small C++ programs (kept in
[`../tools/legacy`](../tools/legacy)):

| Program | Output | Input (not archived) |
| --- | --- | --- |
| `tran4.cpp` | `sin.coe`, `road2.coe`, `music2.txt` | `data3.txt` |
| `tranmusic.cpp` | `music.coe` | `musicmodi.txt` |
| `tranp.cpp` | `putd.coe` | built-in 5×7 digit table |

The chart and track source files were not preserved, so these tools document the formats but
cannot reproduce the shipped charts. The archived `.coe` files remain the canonical data.

The original `1.py` image converter was removed because it contained a hard-coded local path
with a student ID; [`../tools/image2coe.py`](../tools/image2coe.py) replaces it.
